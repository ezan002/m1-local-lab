## 2. 产品目标与成功的样子

目标用户是需要在自己电脑上安装并理解智能体任务的导师、项目研究人员和演示者。产品应让人从一个任务入口看清**问题—计划—Agent/工具动作—证据—结果—状态变化**，再从任一可恢复边界查看历史、继续或建立新分支。导入的外部历史必须始终可识别为“已有记录”，不能伪装成此软件刚执行的任务。

产品成功不由“装了某个框架”判定，而由以下体验判定：第一次使用者能按指南启动；能判断任务是否真的运行、结果依据是什么；能看到失败原因和下一步；能从运行图或列表进入具体步骤；能看出两个分支共享哪里、从哪里修改、结果有何差别；能在导师提供的合法数据上浏览历史轨迹，且不会误触模型或外部动作。界面优先给人可读的摘要，再按需展开安全的原始细节。

本阶段不承诺“多数 benchmark 问题都可正确解决”“可准确自动归因”“完整复刻微软 Magentic-One”或“所有外部网页动作可以回滚”。这些都需要单独的能力定义和实证。

### 五个不可混用的动作

| 动作 | 对已有运行的影响 | 何时可用 | 产品必须说清的代价 |
|---|---|---|---|
| 查看历史 | 只读 | 有保存的运行记录 | 不重新执行，也不调用模型 |
| 暂停 / 继续 | 暂停请求在安全边界生效；继续原运行 | 运行中请求暂停；已暂停或可恢复状态才继续 | 外部动作可能已发生；继续可能再次调用模型或工具 |
| Replay | 从所选非终结checkpoint创建新运行/分支，重新执行后续 | 有合法、已初始化的快照 | 可能再次计费；结果及外部网页状态可能变化 |
| Fork | 修改允许字段，先创建暂停的新分支，再由用户决定是否继续 | 有合法快照和可修改字段 | 创建分支与实际执行应是两个清楚的动作 |
| 导入历史 | 读取外部既有记录 | 已获准的数据和适配格式 | 默认没有本项目可执行checkpoint，不能冒充可Replay的新任务 |

上述是**验收语义**，不是指定必须沿用当前 LangGraph 或 Phoenix 的内部实现。

## 4. 最小端到端验收场景

1. **全新电脑入门**：在独立、无现有数据库的 Windows 环境按交付包安装和启动；打开产品入口，理解服务就绪与缺少模型凭据两种状态；重启后示例运行仍可查。另标记“导师物理电脑验收”结果，不用同机模拟代替。
2. **真实任务可解释**：在明确授权、预算和安全范围内提交一个公开网页或允许文件任务；比对外部事实/文件内容与答案；记录实际节点、工具证据和模型调用。离线RuleBased测试只能证明流程，不证明真实模型答题质量。
3. **回看与控制**：选择已完成运行的合法非终结checkpoint，先只读观察，再经一次明确确认进行Replay；验证原运行未变、新分支血缘和实际重执行节点。另用隔离确定性场景验证Pause/Resume、Fork修改后继续及失败恢复。
4. **分支比较**：同屏显示两支共享的历史、修改位置、不同后续步骤及结果；无差异时也明确显示。若新分支只重做Finalizer，不误称整个浏览过程已重做。
5. **外部历史**：用获准的小样本导入或读取历史；在产品里查看来源、截断和可显示的步骤；确认它不出现在“本项目刚执行”列表，也没有本地Replay入口。原始数据缺失时显示准备说明而非虚构案例。
6. **故障路径**：模拟Phoenix/观测不可用、浏览器启动失败、模型凭据缺失、非法checkpoint、恢复边界不确定、页面刷新；主任务与观测故障分开提示，提供下一步，且不会因页面重试重复提交。
7. **安全与费用**：在每个可能调用真实模型或外部工具的动作前提供明确确认；验证授权文件/网页范围、敏感字段隐藏和外部数据许可边界。记录真实调用、token与费用证据的来源；没有账单时不填估算成实收费用。

验收结论按“**产品行为PASS/PARTIAL/BLOCKED**”及“**证据类型：自动测试／现场真实运行／模拟数据／仅设计**”分别记录。一个成功案例不推出“大多数任务成功”；模型答案正确性必须独立核对。P0场景先形成能连续演示的主线，再决定P1/P2投入。

## 5. 当前基线与产品缺口

现有LangGraph图、FastAPI/SSE、SQLite检查点、官方WebSurfer适配、文件读取、只生成代码的Coder、OTel/Phoenix以及外部历史旁路均有实现。既有审查记录为**130 passed、2 skipped**、同机隔离安装通过；两项skip涉及真实模型/WebSurfer。2026-09-20的现场演示又观察到一次真实公开网页任务和一次从`next=finalizer`快照进行的真实Replay。这些是历史证据；本阶段没有重跑测试，也没有重新核验当前服务状态。

产品层面的主要缺口是：第一次使用仍需分别处理应用和Phoenix；完整Span需去6006；运行步骤、证据与状态分散；刷新后选择不保留；分支关系缺少直观比较；导入历史主要呈现规范化摘要，部分结构化内容省略；新clone没有研究数据；另一台物理电脑未完成验收。应先验证这些问题对目标用户的影响，再决定保留、替换或封装现有组件。历史README底部仍有“gRPC通配监听、跨进程所有权未解决”等过期表述，审查报告和对应代码已记录修复；不要以过期段落判断当前缺陷。

## 6. 非目标与待决架构

本阶段不设计界面原型、不迁移技术、不修改运行时模型配置、不升级依赖、不运行付费任务、不重跑归因基准、不下载新数据、不移动或清理数据库。现有归因代码与冻结研究结果保持原状；“隐藏或调整主界面入口”的具体交互策略属于后续设计阶段，当前不作实现承诺。
